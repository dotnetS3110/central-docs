GITLAB REPOSITORY SETUP

Quick guide to pushing projects to GitLab effortlessly using SSH security, safe branch check-in workflow, and troubleshooting.

01

Navigate to Folder

cd existing_folder
02

Initialize Git

git init --initial-branch=main --object-format=sha1
03

Add Remote

git remote add origin git@ws-srv-git.in.webmyne.com:template/modernize-angular-admin-panel.git
04

Commit & Push

git add .
git commit -m "Initial commit"
git push --set-upstream origin main

🔐 SSH Security Setup

Ensure your secure connection by configuring SSH keys.

ssh-keygen -t ed25519 -C "your_email@example.com"
ssh-add ~/.ssh/id_ed25519

Copy your public key and add it to GitLab Settings:

cat ~/.ssh/id_ed25519.pub
🧪
Test connection: ssh -T git@ws-srv-git.in.webmyne.com
⚠️

Note: For custom keys, configure ~/.ssh/config.

🔀 Step-by-Step Workflow

Check In to Main Branch

Standard workflow for safely merging your feature/working branch into main using Visual Studio GUI or Git CLI.

Direct Anchor: #check-in-to-main
1 Your Branch Commit & Push
➔
2 Main Branch Fetch & Pull Latest
➔
3 Sync to Branch Merge Main & Resolve Conflicts
➔
4 Merge to Main Merge Branch into Main
➔
5 Deploy Push Main to GitLab
01

Check you are in your current branch

🔷 Visual Studio & CLI

Verify your active branch before staging changes. Ensure you are working on your assigned feature/bugfix branch and not directly making edits on main.

Visual Studio:

Check the bottom-right status bar or the branch label at the top of the Git Changes window (e.g., feature/your-branch).

git branch --show-current
02

Stage Changes using (+)

🔷 Visual Studio & CLI

Stage all your modified and newly added files so they are prepared for committing.

Visual Studio:

Open the Git Changes panel (View → Git Changes or Ctrl+0, Ctrl+G). Under the Changes header, click the + (Stage All) icon, or click + next to individual files. 

git add .
03

Commit changes and push into your branch

🔷 Visual Studio & CLI

Save your staged snapshot locally with a descriptive commit message, then push it to your remote feature branch on GitLab.

Visual Studio:

Type your commit message in the text area, click Commit Staged, then click the Push button (up arrow ↑) in the Git Changes toolbar or status bar. 

git commit -m "feat: your descriptive commit message"
git push origin HEAD
04

Switch to main and fetch & pull changes

🔷 Visual Studio & CLI

Switch your local workspace to the main branch and pull the latest changes submitted by team members from the remote repository.

Visual Studio:

Click the branch picker at the bottom-right status bar and select main. Then in the Git Changes panel, click Fetch followed by Pull (or down arrow ↓). 

git checkout main
git pull origin main
05

Switch back to your branch

🔷 Visual Studio & CLI

Switch back to your active feature branch so you can safely incorporate the latest updates from main.

Visual Studio:

Click the branch selector in the bottom-right status bar or Git Repository window and checkout your branch.

git checkout <your-branch-name>
06

Right click on main branch and merge changes to your branch

🔷 Visual Studio & CLI

Merge the freshly updated main branch into your feature branch. This ensures any merge conflicts or integration issues are tested and resolved in your branch first, protecting main.

Visual Studio:

Open Git Repository (Git → Manage Branches or Ctrl+0, Ctrl+R). Under Local Branches, right-click on main and choose "Merge into Current Branch". If any conflicts arise, resolve them using the VS Merge Conflict Editor and click Commit Merge. 

git merge main
💡 Testing Checkpoint: Build and run your project now to confirm everything compiles and passes tests!
07

Switch to main branch

🔷 Visual Studio & CLI

Now that your working branch is fully tested, conflict-free, and up to date with main, switch back to the main branch.

Visual Studio:

Use the bottom-right branch dropdown or Git Repository window to checkout main.

git checkout main
08

Right click on your branch and merge changes to main branch

🔷 Visual Studio & CLI

Merge your feature branch into main. Because you already resolved all conflicts in Step 6, this merge will complete cleanly with zero conflicts!

Visual Studio:

In the Git Repository window (Git → Manage Branches), under Local Branches, right-click on your branch and select "Merge into Current Branch" (merging your branch into main). 

git merge <your-branch-name>
09

Push changes to main

🔷 Visual Studio & CLI

Push your newly merged main branch directly to the remote GitLab repository to make your changes live for the entire team.

Visual Studio:

In the Git Changes window or status bar, click the Push button (up arrow ↑) or go to Git → Push.

git push origin main
🎉 All Done! Your changes are now safely checked in to the remote main branch.
🛡️

Why this workflow keeps main safe:

By merging main into your feature branch first (Step 6), all conflict resolutions and testing occur locally on your branch. main is never broken by an untested merge conflict!

🔍 Host Key Mismatch Troubleshooting

Detailed troubleshooting guide for when Visual Studio or Git reports host identification changes or mismatches.

1. The Issue

While performing Git Fetch/Pull from Visual Studio, the following error occurred:

WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!

IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!
Someone could be eavesdropping on you right now (man-in-the-middle attack)!

Offending ECDSA key in /c/Users/vansh/.ssh/known_hosts:4
Host key for ws-srv-git.in.webmyne.com has changed and you have requested strict checking.
Host key verification failed.

fatal: Could not read from remote repository.

Note: Git fetch was failing even though SSH authentication itself was working.

2. Repository Information

Local Repository: D:\Vansh\Projects\CGD\CharotalGAS\Charotar_GAS
Git Remote: origin git@ws-srv-git.in.webmyne.com:city-gas-distribution-cgd/charotar_gas.git

The remote repository URL is correct and valid.

A

Initial Connection Test

First, test if GitLab SSH authentication works directly:

ssh -T git@ws-srv-git.in.webmyne.com

Expected Response: Welcome to GitLab, @vansh!

This confirms that SSH authentication is working, the SSH key is valid, and GitLab permissions are correct. The problem is strictly an SSH host-key verification issue.

B

Stale Host Key

SSH reported: Offending ECDSA key in /c/Users/vansh/.ssh/known_hosts:4

This means your local known_hosts file contains an old SSH host key for ws-srv-git.in.webmyne.com. This usually happens when the Git server is rebuilt, migrated, has keys regenerated, or IP/DNS settings change.

⚠️

Always verify key changes with your administrator before accepting a new key to prevent man-in-the-middle attacks.

C

Key Finding: Different SSH Clients

Troubleshooting revealed that PowerShell and Git resolved hostnames to different IP addresses and keys:

Normal PowerShell SSH
↓

ws-srv-git.in.webmyne.com

↓

192.168.1.231

↓ ED25519 SHA256:gqDFXIUdI1Bdj0PUPsaKBGhfxYpgs3P2nXtImYwSHBA
Git Fetch SSH Process
↓

ws-srv-git.in.webmyne.com

↓

192.168.1.254

↓ ED25519 SHA256:eaJLX1fgTmjh9N+GcTkNNm/TK/QM1LW1UD9bsy235tk

This mismatch indicates Git and standard PowerShell SSH were connecting to different targets/gateways.

D

Investigating SSH Executable Differences

Checking the environment paths:

where.exe ssh

Response: C:\Windows\System32\OpenSSH\ssh.exe

Checking Git's configured SSH command:

git config --show-origin --get core.sshCommand

Response: None (empty)

By default, Git uses its own built-in Git-for-Windows SSH environment (e.g., OpenSSH_8.7p1 reading /etc/ssh/ssh_config) which resolves hosts differently than the Windows System32 OpenSSH environment.

1

Remove the Old Host Key

Run the following command to purge the stale host key from your known hosts file:

ssh-keygen -R ws-srv-git.in.webmyne.com -f "$env:USERPROFILE\.ssh\known_hosts"

Verify that the entry is gone:

ssh-keygen -F ws-srv-git.in.webmyne.com -f "$env:USERPROFILE\.ssh\known_hosts"

This check should return no output, confirming the key was successfully cleared.

2

Configure Git to use Windows OpenSSH

Force Git to use the same Windows OpenSSH client as PowerShell. This aligns the hostname resolution and key cache between both environments:

git config --global core.sshCommand "C:/Windows/System32/OpenSSH/ssh.exe"

Verify global configuration:

git config --global --get core.sshCommand

Expected Response: C:/Windows/System32/OpenSSH/ssh.exe

3

Verify SSH & Git Fetch

First, perform a direct SSH test again to register the new key if prompted:

ssh -T git@ws-srv-git.in.webmyne.com

If prompted to accept a new host key, verify the fingerprint matches your server's active key before entering yes.

Now, test Git fetch:

git fetch origin

Git should now fetch without host key verification failures!

4

Optional Verbose Debugging

If issues persist, trigger verbose SSH logging on the fetch command to pinpoint key loaders, file paths, or target IPs:

$env:GIT_SSH_COMMAND="C:\Windows\System32\OpenSSH\ssh.exe -v"
git fetch origin

Inspect output for lines such as Connecting to..., Server host key..., load_hostkeys, and UserKnownHostsFile.

After debugging, clean up the temporary environment variable:

Remove-Item Env:GIT_SSH_COMMAND
🛡️

12. Important Security Note

A changed SSH host key is a serious warning but doesn't always indicate a security attack. It is frequently caused by server upgrades, rebuilds, IP reassignments, or DNS shifts. However, never bypass verification blindly: always confirm the new fingerprint with your Git/server administrator.

In this scenario, two different fingerprints were active due to resolving to separate IPs (192.168.1.231 vs 192.168.1.254). This is a network/DNS level issue that should be raised to network administrators if both continue to be used.

13. Final Quick-Fix Commands

# 1. Remove old host key
ssh-keygen -R ws-srv-git.in.webmyne.com -f "$env:USERPROFILE\.ssh\known_hosts"

# 2. Test SSH
ssh -T git@ws-srv-git.in.webmyne.com

# 3. Configure Git to use Windows OpenSSH
git config --global core.sshCommand "C:/Windows/System32/OpenSSH/ssh.exe"

# 4. Verify Git SSH configuration
git config --global --get core.sshCommand

# 5. Fetch repository
git fetch origin

14. Root Cause Summary

Root Cause: The Git repository was accessible, and the user's SSH authentication was valid. The failure was caused by an SSH host-key mismatch combined with Git using a different SSH environment/server resolution than the normal PowerShell SSH command.

Solution: Purge the stale host key from known_hosts, verify the new server fingerprint, confirm SSH connection via ssh -T, configure Git to explicitly use Windows OpenSSH, and fetch again.

Successfully Setup!
