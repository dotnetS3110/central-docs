Quick guide to pushing projects to GitLab effortlessly using SSH security, safe branch check-in workflow, and troubleshooting host key changes.

cd existing_folder

Initialize Git

git init --initial-branch=main --object-format=sha1

Add Remote

git remote add origin git@ws-srv-git.in.webmyne.com:template/modernize-angular-admin-panel.git
04

Commit & Push

git add .
git commit -m "Initial commit"
git push --set-upstream origin main

🔐 SSH Security Setup

Ensure your secure connection by enabling the Windows SSH agent service and configuring SSH keys.

1. Enable & Start Windows SSH Agent Service (PowerShell Run as Admin):

Get-Service ssh-agent
Set-Service -Name ssh-agent -StartupType Automatic
Start-Service ssh-agent

2. Generate SSH Key & Add to Agent:

ssh-keygen -t ed25519 -C "your_email@example.com"
ssh-add ~/.ssh/id_ed25519

3. Copy Public Key to GitLab:

cat ~/.ssh/id_ed25519.pub
🧪
Test connection: ssh -T git@ws-srv-git.in.webmyne.com
⚠️

Note: If ssh-add errors with "unable to start ssh-agent service", verify that ssh-agent service startup type is set to Automatic and started via the commands in Step 1.

🔀 Step-by-Step Workflow

Check In to Main Branch

Standard workflow for safely merging your feature/working branch into main using Visual Studio GUI or Git CLI.

Direct Anchor: #check-in-to-main
1 Your Branch Commit & Push
➔
2 Main Branch Fetch & Pull Latest
➔
3 Sync to Branch Merge Main & Resolve Conflicts
➔
4 Merge to Main Merge Branch into Main
➔
5 Deploy Push Main to GitLab
01

Check you are in your current branch

🔷 Visual Studio & CLI

Verify your active branch before staging changes. Ensure you are working on your assigned feature/bugfix branch and not directly making edits on main.

Visual Studio:

Check the bottom-right status bar or the branch label at the top of the Git Changes window (e.g., feature/your-branch).

git branch --show-current
02

Stage Changes using (+)

🔷 Visual Studio & CLI

Stage all your modified and newly added files so they are prepared for committing.

Visual Studio:

Open the Git Changes panel (View → Git Changes or Ctrl+0, Ctrl+G). Under the Changes header, click the + (Stage All) icon, or click + next to individual files. 

git add .
03

Commit changes and push into your branch

🔷 Visual Studio & CLI

Save your staged snapshot locally with a descriptive commit message, then push it to your remote feature branch on GitLab.

Visual Studio:

Type your commit message in the text area, click Commit Staged, then click the Push button (up arrow ↑) in the Git Changes toolbar or status bar. 

git commit -m "feat: your descriptive commit message"
git push origin HEAD
04

Switch to main and fetch & pull changes

🔷 Visual Studio & CLI

Switch your local workspace to the main branch and pull the latest changes submitted by team members from the remote repository.

Visual Studio:

Click the branch picker at the bottom-right status bar and select main. Then in the Git Changes panel, click Fetch followed by Pull (or down arrow ↓). 

git checkout main
git pull origin main
05

Switch back to your branch

🔷 Visual Studio & CLI

Switch back to your active feature branch so you can safely incorporate the latest updates from main.

Visual Studio:

Click the branch selector in the bottom-right status bar or Git Repository window and checkout your branch.

git checkout <your-branch-name>
06

Right click on main branch and merge changes to your branch

🔷 Visual Studio & CLI

Merge the freshly updated main branch into your feature branch. This ensures any merge conflicts or integration issues are tested and resolved in your branch first, protecting main.

Visual Studio:

Open Git Repository (Git → Manage Branches or Ctrl+0, Ctrl+R). Under Local Branches, right-click on main and choose "Merge into Current Branch". If any conflicts arise, resolve them using the VS Merge Conflict Editor and click Commit Merge. 

git merge main
💡 Testing Checkpoint: Build and run your project now to confirm everything compiles and passes tests!
07

Switch to main branch

🔷 Visual Studio & CLI

Now that your working branch is fully tested, conflict-free, and up to date with main, switch back to the main branch.

Visual Studio:

Use the bottom-right branch dropdown or Git Repository window to checkout main.

git checkout main
08

Right click on your branch and merge changes to main branch

🔷 Visual Studio & CLI

Merge your feature branch into main. Because you already resolved all conflicts in Step 6, this merge will complete cleanly with zero conflicts!

Visual Studio:

In the Git Repository window (Git → Manage Branches), under Local Branches, right-click on your branch and select "Merge into Current Branch" (merging your branch into main). 

git merge <your-branch-name>
09

Push changes to main

🔷 Visual Studio & CLI

Push your newly merged main branch directly to the remote GitLab repository to make your changes live for the entire team.

Visual Studio:

In the Git Changes window or status bar, click the Push button (up arrow ↑) or go to Git → Push.

git push origin main
🎉 All Done! Your changes are now safely checked in to the remote main branch.
🛡️

Why this workflow keeps main safe:

By merging main into your feature branch first (Step 6), all conflict resolutions and testing occur locally on your branch. main is never broken by an untested merge conflict!

⚠️ Troubleshooting Guide

🔍 Git SSH – Remote Host Identification Changed

Comprehensive resolution guide for when Git or Visual Studio detects an SSH host identification mismatch during fetch or pull operations.

Direct Anchor: #troubleshooting

1. Visual Studio / Git Error Output

While fetching or pulling a Git repository from Visual Studio, the following error may occur:

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@

IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!
Someone could be eavesdropping on you right now (man-in-the-middle attack)!

It is also possible that a host key has just been changed.

The fingerprint for the ED25519 key sent by the remote host is
SHA256:gqDFXIUdI1Bdj0PUPsaKBGhfxYpgs3P2nXtImYwSHBA.

Add correct host key in C:\Users\vansh/.ssh/known_hosts to get rid of this message.

Offending ED25519 key in C:\Users\vansh/.ssh/known_hosts:2

Host key for ws-srv-git.in.webmyne.com has changed and you have requested strict checking.

Host key verification failed.

Note: Git rejects the remote host connection because strict checking detected that the host key stored locally differs from the server's key.

2. Connection & Key Context

The error message reveals the exact parameters involved in this mismatch:

Git Server Host: ws-srv-git.in.webmyne.com
SSH Known-Hosts File: C:\Users\vansh\.ssh\known_hosts
Offending Line Entry: Line 2
New ED25519 Fingerprint: SHA256:gqDFXIUdI1Bdj0PUPsaKBGhfxYpgs3P2nXtImYwSHBA
💡 The offending key on Line 2 in known_hosts prevents any fetch, pull, or push operation until updated.
!

What Causes This Error?

This error occurs when the SSH host key stored on the local computer does not match the host key currently provided by the Git server.

The SSH client stores previously verified host keys in your known_hosts file. When reconnecting, SSH verifies the remote server's cryptographic identity against that stored fingerprint. If they do not match, SSH intentionally blocks the connection to protect against potentially connecting to an impersonated server.

📋

Common Reasons Include:

A host key difference typically happens due to one of the following reasons:

1 Git server was rebuilt or reinstalled (fresh server installation generated new host keys).
2 SSH host keys were regenerated by the administrator.
3 Git server was migrated to another machine or platform.
4 Server infrastructure or IP was changed.
5 The old SSH host key is still stored in the local known_hosts file.
6 Security risk: In rare cases, the connection could be subject to a man-in-the-middle (MITM) attack.
1

Step 1 – Verify the New Server Fingerprint

Before removing the old key, confirm with the Git/server administrator that the new fingerprint is legitimate:

SHA256:gqDFXIUdI1Bdj0PUPsaKBGhfxYpgs3P2nXtImYwSHBA
⚠️

Crucial Rule: Do not blindly accept a changed host key without verification.

2

Step 2 – Remove the Old SSH Host Key

Open PowerShell and execute:

ssh-keygen -R ws-srv-git.in.webmyne.com

This removes the old host-key entry from: C:\Users\vansh\.ssh\known_hosts

3

Step 3 – Test the SSH Connection

Run the test connection command:

ssh -T git@ws-srv-git.in.webmyne.com

SSH will ask whether the new host should be trusted:

The authenticity of host 'ws-srv-git.in.webmyne.com' can't be established.

ED25519 key fingerprint is
SHA256:gqDFXIUdI1Bdj0PUPsaKBGhfxYpgs3P2nXtImYwSHBA.

Are you sure you want to continue connecting
(yes/no/[fingerprint])?

After confirming the fingerprint, enter:

yes

✓ The new host key will then be added to the known_hosts file.

4

Step 4 – Retry Git Fetch / Pull

After successfully establishing the SSH connection, return to Visual Studio and perform:

Git → Fetch

or:

Git → Pull

✓ The repository should now connect to the Git server normally.

Alternative

Manual Solution

If the command does not work, open the SSH known-hosts file:

notepad C:\Users\vansh\.ssh\known_hosts

The error indicates that the offending key is on: Line 2

  1. Remove the old entry for ws-srv-git.in.webmyne.com (on Line 2).
  2. Save the file.
  3. Then test the connection again:
ssh -T git@ws-srv-git.in.webmyne.com

Confirm the new fingerprint when prompted.

⚡ Quick Fix

For a server change that has already been verified by the administrator:

ssh-keygen -R ws-srv-git.in.webmyne.com

ssh -T git@ws-srv-git.in.webmyne.com

git fetch

🔍 Verification

After fixing the host key, verify the remote repository:

git remote -v

Then test:

git fetch
🎉 If the fetch completes successfully, the SSH host-key issue has been resolved.
🛡️

Important Note

The known_hosts file stores SSH host keys for servers that the computer has previously connected to. SSH compares the stored key with the key received from the server.

If the keys do not match, SSH blocks the connection to protect against potentially connecting to an impersonated server.

Therefore, always verify the new server fingerprint before trusting a changed host key.

✓

Successfully Setup!

Your repository is now connected and ready for deployment.
